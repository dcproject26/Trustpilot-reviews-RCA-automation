# ORM RCA — Data-Source Spec (source of truth)

This document tells you where every value on the dashboard comes from, which pipeline step produces it, which DB column stores it, and what still needs fixing. Use it as the contract. When a field is wrong, fix it at the source named here — not by patching the UI.

**Rule of thumb for origin:**
- **BigQuery** owns booking *facts* (IDs, experience, vendor, dates).
- **Zendesk** owns anything that *happened in support* (timeline, refund, real guest name, booking status).
- **Claude** owns anything *written or judged* (translation, classification, RCA, reply, ticket-facts extraction).
- **Google Sheet** owns DSS policy, canned response tone, and the RCA checklist.
- **Computed** = derived in Python. **Ingest** = the review post itself.

Do not turn to Claude for a value BigQuery or Zendesk already has. Do not turn to BigQuery for anything that only exists in a ticket body.

---

## 0. Goal

One negative Trustpilot review comes in → match it to a real booking → pull the real facts from BigQuery + Zendesk → classify → write an RCA grounded in those facts → draft a guest reply → present it on the dashboard for an associate to verify, edit, and send. Nothing is auto-sent to the guest. MOCK_MODE gates every external call.

---

## 0.5. Field ownership at a glance
```
BigQuery owns:  booking IDs, experience/vendor/TID data, dates, ratings, completion, similars
Zendesk owns:   timeline, real guest name, booking status, refund, CE actions, ticket_mail_seen
Claude owns:    translation, classification, RCA text, response draft, ticket-facts extraction
Sheets own:     DSS policy, canned response tone, RCA CHECKLIST (diagnostic checks: General + CE + RO + 16 scenarios)
Computed owns:  match tier, confidence trail, lead time, tab routing
Ingest owns:    review body, author, rating, timestamp
```
If a field is wrong, first identify which owner is authoritative — then fix at that source.

## 2. External source reference

**BigQuery tables** (`server/config.py`):
- `fct_bookings` — booking record (the `draft.booking` dict is built from here)
- `fct_reviews` — ratings / review history (insights, similar reviews)
- `fct_fulfilments` — fulfilment status + **real ticket-sent timestamps** (completion, same-day, timeline times)
- `fct_support_queries` — support-query counts (support ratio insights)

**`draft.booking` dict keys** (the contract the UI reads — populated by BQ match):
`id, experienceName, tgid, tid, vid, vidName/partner, fulfilmentType, bookedOn, visitDate, pax, amount, status, guestName` — note `guestName` from BQ is a **privacy hash**, not usable.

**Zendesk** (`server/config.py`): tickets fetched via Zendesk search with `fieldvalue:<bid>` — matches any custom field carrying the BID (proven in `zendesk.py:186`, matches the 2024 Retool code). Falls back to free-text search on `"<bid>"` (`zendesk.py:191`). Custom field IDs for direct reads on returned tickets: BookingID `360021524471`, TGID `360024198092`, TID `360024232711`. `timeline_raw` = raw comment bodies (what Claude reads); `timeline` = display events.

**Claude** = Replit AI Integration.

**Google Sheets:**
- **DSS** `1sz8KkxiBaGSxiQy4G-iPN_0gmzGg4wt3V8NI0MaVd88` — resolution policy (CE/RO), scored on L1/L2.
- **Canned responses** `1aXnZzzFQ8tDiaXs0E2YRErOcTSOsbTOqnM7WhyOnmi4` — response tone examples.
- **RCA Checklist** `1RpvQCz35_pOTnWGrYL0rfPKUXejmt5KeBppgI9QTYJ8` (gid `1186061023`) — the diagnostic checks: General Guidelines + CE Error + RO Error + 16 scenario checklists. **Baked into `server/checklist.py`** as structured data (the sheet is a merged-cell layout that won't parse as clean CSV); re-sync from the sheet when CX edits it. This sheet is the authoritative source for Column 3's diagnostic checks.

## 4. Ticket-facts extraction — fills the Zendesk-sourced Col-2 gaps

Guest name, booking status, refund, etc. live **inside the ticket prose**, not in clean columns. Run one Claude pass after Zendesk enrichment (step 5b), store as `draft.ticket_facts`, then fill Col-2 fields from it (BQ as fallback). Every fact carries an evidence ticket id.

Prompt: see **§8.2**.

**Wiring:** run once per review on the full `timeline_raw`. Then:
- `guest name = ticket_facts.guest_full_name || review.author`
- `booking status = ticket_facts.booking_status || booking.status`
- `refund / resolution` → feed into RCA generation (step 12)

1. **Match confidence** — map `draft.match_confidence` to the UI (Tier-1 attachment ⇒ `"high"`).

## 6. Client — one normalization layer (stops the crashes)

The render code was built for a hardcoded demo array (rich nested shape, every field present). Live `/api/reviews/{id}` is flat and partial, so `x.length` / `x.value` on a missing field white-screens the page. Fix once, centrally:

- Add `toViewModel(api, ins)` that returns an object where **every field the renderer touches exists**, defaulted (`[]` lists, `''` text, `{value:'—',sub:'',tone:'gray'}` tiles).
- Route `loadDraftOverlays` through it — render only from the view-model, never the raw API.
- Guard remaining accesses: `(x || []).length`, `(obj || {}).value`.
- If a field is mis-mapped, fix it **inside `toViewModel` only**, never in the renderer.

Result: a missing field renders "—", never a crash.

## 7. Guardrails (do not violate)

- **MOCK_MODE stays as configured.** Every external call has a mock fallback; `is_live(service)` gates it.
- **No deploy.** No auto-send to the guest. Send posts the RCA to the Slack thread; the reply copy is copied from the dashboard and posted to Trustpilot **manually**.
- **Response copy is NEVER included** in the Slack RCA post.
- **Manual (`C_MANUAL`) reviews never post to Slack** (guard already exists in the pipeline).
- Fix values at the **source named in §3**, not by hardcoding in the UI.
- Keep both test suites green.

## 8. AI prompts — the source of every Claude-owned field

All Claude calls live in `server/prompts.py`. Each prompt has one job. All return strict JSON (except translation/stated-issue/response, which return plain text), no markdown, no preamble. Every extracted fact must be inferable from the inputs — no fabrication.

### 8.1 Translation — step 1
```
SYSTEM:
You are a translation engine. Translate customer reviews from any source language into clear,
natural English, preserving tone, facts, and any names/dates/IDs. Do NOT summarise, interpret,
or add commentary.
USER:
=== SOURCE LANGUAGE ===
{source_language}
=== ORIGINAL REVIEW TEXT ===
{review_body_original}
Rules: preserve all names/places/dates/times/amounts/IDs verbatim; no bracketed notes; don't
soften strong language; return only the translation — no label, no source text.
Return plain text. No JSON, no markdown, no preamble.
```

### 8.2 Ticket-facts extraction — step 5b
```
SYSTEM:
You are a data-extraction engine for Headout's ORM system. You read the raw Zendesk
support-ticket comments for ONE booking and extract structured facts. You NEVER invent data.
If a fact is not explicitly present, return null. Every value must be copyable from the ticket
text. Return STRICT JSON only — no markdown, no preamble.
USER:
=== BOOKING (from BigQuery — authoritative for IDs/dates) ===
{booking_json}
=== ZENDESK TICKET COMMENTS (chronological, raw bodies) ===
{timeline_raw}
Extract using ONLY the text above. Null for anything not explicitly stated. Do not guess.
Return STRICT JSON matching this schema exactly:
{
  "guest_full_name": null, "booking_status": null, "is_same_day_booking": null,
  "is_cancellable": null, "is_reschedulable": null, "sla_breached": null,
  "ticket_email_seen": null, "interaction_tags": [], "delay_or_issue_reason": null,
  "refund": {"issued": null, "amount": null, "reference_id": null, "out_of_policy": null},
  "ce_actions": [], "resolution_summary": null, "primary_issue": null, "evidence": {}
}
FIELD RULES:
1. GENERAL — null over guessing. Every non-null scalar needs an `evidence` entry naming the
   ticket (e.g. {"guest_full_name":"ZD-34011333"}); missing evidence = force null. Ticket ids
   appear as headers like [ZD-34011333] — copy the numeric id.
2. guest_full_name — only a plain human name from prose ("Hey David Hultsman," → "David
   Hultsman"). Reject base64/hash/URL-encoded/masked values → null. Prefer the name the CE
   addresses ("Hey X,").
3. booking_status — only from an explicit status line. Normalise to one of PENDING, CONFIRMED,
   FULFILLED, CANCELLED, REFUNDED (fulfilled/complete/completed→FULFILLED; canceled→CANCELLED;
   "refund processed"→REFUNDED). Anything else → null.
4. Booleans (is_same_day_booking, is_cancellable, is_reschedulable, sla_breached,
   ticket_email_seen, refund.issued, refund.out_of_policy) — true/false/null only, from explicit
   statements ("Is Cancellable: No"→false). "N/A"/"Unknown"/absent → null.
5. interaction_tags — copy tag strings verbatim (e.g. "delay_fulfilment__delay__sp_dependency").
   None → [].
6. delay_or_issue_reason — one factual sentence on WHY; no guest emotion; absent → null.
7. refund — issued true on "refund processed"/"amount refunded", false if explicitly denied,
   else null. amount as "<CCY> <N.NN>" (use booking currency if none stated). reference_id
   verbatim. out_of_policy true on "out of policy"/"exception".
8. ce_actions — verb-first, grounded ("Refunded USD 19.42 as exception"). No "investigated" /
   "helped". Empty [] if none.
9. resolution_summary — one neutral sentence on the outcome; null if none.
10. primary_issue — one sentence from the CE's classification (not guest words); null if none.
11. evidence — {field → ticket id} for every non-null scalar; dotted keys for nested
    (refund.amount); arrays need none.
OUTPUT: the JSON only. No preamble, no fences.
```

### 8.3 Timeline shaping — step 6 (event summarisation)
```
SYSTEM:
You shape raw Zendesk ticket comments into a clean Events Timeline (time · thread · label ·
summary). You NEVER invent CE actions, SP responses, times, or comp amounts. Unintelligible
body → keep=false. Return STRICT JSON only — a list of event objects.
USER:
=== BOOKING (context) ===
{booking_json}
=== REAL FULFILMENT TIMES (from BigQuery fct_fulfilments) ===
{fulfilment_times_json}   // booking_created_at, ticket_sent_at — may be null
=== REVIEW POSTED ON: {review_pub_date} ===
=== REVIEW PREVIEW: "{review_body_preview}" ===
=== RAW ZENDESK EVENTS (chronological, unshaped) ===
{raw_events_json}
RULES:
1. Per event decide keep vs drop, then produce a clean frame. Drop: empty/whitespace bodies,
   pure signature/logo HTML, internal syncs with no operational meaning, standalone acks.
2. GROUP consecutive same-timestamp events that are one action across comments; set
   idx_range=[first,last] (e.g. three 15:41 macro outputs → one "CE pulled up case context").
3. LABEL = short verb-first phrase (what happened, not the source). No "[ZD-###]". Examples:
   "Guest reached out", "Guest reply", "CE response", "CE pulled up case context",
   "Minded AI response", "Skyler chat opened", "SP response", "CE prepared vendor login",
   "Ticket generated", "Refund processed", "System event".
4. SUMMARY = one neutral factual sentence. No HTML/logo/macro dumps; summarise the ACTION, not
   field dumps; never invent CE reasoning or SP responses.
5. THREAD: "Skyler chat"/"conversation with web user" → chat; SP-brand → sp; else keep input.
6. ACTOR: guest→guest; co→support; ai(Minded/Skyler/bot)→ai; sp→sp; system→system (usually drop).
7. NEVER INVENT. Every summary inferable from raw_body; else summary "Internal system event.",
   keep=false.
SYNTHETIC EVENTS — inject ONLY from REAL data, never fabricate a clock time:
  • Booking created — time = fulfilment_times.booking_created_at IF present, else
    "{booking.bookedOn}" (DATE ONLY, no clock time). label "Booking created",
    summary "Guest booked <experience>."
  • Tickets sent — ONLY IF fulfilment_times.ticket_sent_at is present. time = that value.
    label "Tickets sent", summary "Voucher emailed." Do NOT state "within 1 min" or any
    duration unless both timestamps are real and you computed the gap. If ticket_sent_at is
    null, OMIT this event.
  • Review posted — time = "{review_pub_date}", label "Review posted",
    summary "Negative Trustpilot review posted with BID <bid> referenced."
OUTPUT: JSON list of shaped events, chronological. No preamble.
```

### 8.8 Response draft — step 13
```

USER:
=== REVIEW ===

Body: {review_body_english}
=== CLASSIFICATION ===
{classification_json}
=== RCA RESOLUTION (what we're offering) ===
{resolution_text}
=== CANNED RESPONSE EXAMPLES (from Canned sheet — Headout tone) ===
```
